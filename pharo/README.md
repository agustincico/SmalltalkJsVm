# Pharo compatibility for SqueakJS

Pharo's **64-bit** builds render exclusively through SDL2/OSWindow via native FFI, which does
not exist in a browser. Two startup scripts put the classic VM display/input classes back, so
the image renders through `Display`/BitBlt the way SqueakJS can drive it:

- **`startup-compat64.st`** — for **Pharo 10 and 11**, whose 64-bit builds still ship
  `DisplayScreen` (pruned, but present). It restores:
  - `EventSensorConstants`, `InputEventHandler`, `InputEventSensor`, `InputEventFetcher`
    (classic VM event polling) and the classic `HandMorph` event-queue methods,
  - the classic `DisplayScreen` protocol (`beDisplay`, `forceToScreen:`, `deferUpdates:` …),
  - `VMWorldRenderer` + its update modes (rendering via Display/BitBlt),
  - cursor primitives (`beCursor`, `beCursorWithMask:`),

  all extracted verbatim from the Pharo 10 32-bit build, then reinstalls the UI
  (`UIManager default:` after clearing `MainWorldRenderer`).

- **`startup-compat13.st`** — for **Pharo 12 and 13**, which removed `DisplayScreen` and the
  `Display` global outright and dropped the chunk reader's method directive. It is
  `startup-compat64.st` plus a whole port of `DisplayScreen`, with every method installed via
  `compile:classified:` instead of `methodsFor:`. Generated by `utils/mk-compat13.py` from the
  Pharo 10 32-bit `.sources`; regenerate rather than hand-edit.

**32-bit Pharo images need neither script.**

**Usage:** name the script `startup.st` and put it next to the `.image` — Pharo's
`StartupPreferencesLoader` runs it at boot. The `run/` launcher does this on its own: when you
drop a bare `.image` it reads the bytes, and if they are a 64-bit Pharo it fetches the matching
script into the virtual FS before booting (see `pharoCompatScript` in `run/index.html`). It
tests for the *capability* — a standalone `DisplayScreen` class name in the image — rather than
the version number, so a new build picks whichever of the two scripts fits it. A script the
image already ships wins; the launcher never clobbers one.

Verified booting to a clean, interactive world: Pharo 10 (32 and 64), 11, 12, 13 — including
the snapshot image the Pharo Launcher installs today.

**Not yet:** the in-development Pharo 14 and 15 builds pick `startup-compat13.st` but do not
come up — the script's class definitions fail there (`InputEventFetcher` ends up undeclared),
leaving a blank screen. Whatever changed in their class-definition protocol has to be found
before the script applies again.

## The Morphic application (`pharo-app.zip`)

The app is `app-startup.st`: it defines the bubbles demo, clears the IDE chrome (windows,
menubar, taskbar, halos) and builds the running world. `app-snapshot.st` appended to it saves
an image with the app already alive, and that saved image is what gets published — it comes
up showing the application instead of a Pharo desktop that slowly turns into one.

    cat pharo/app-startup.st pharo/app-snapshot.st > startup.st

Run that beside a stock Pharo 10 32-bit image *in the browser worker* (under Node the
FileAttributesPlugin has no virtual FS and every stat fails). It drops an `appbuild.done`
marker once the image is written. Ship that image plus its `.changes` and **no `startup.st`**.

### Making a snapshot resume alive

`Smalltalk snapshotPrimitive` on its own writes an image that comes back completely frozen: it
never re-registers its input semaphore, its delay timer or its display with the VM. Pharo does
that re-registration in `SessionManager>>launchSnapshot:andQuit:`, *around* the primitive —
`currentSession stop:` before, `installNewSession` + `currentSession start:` after — and
`app-snapshot.st` performs that sequence by hand, inside `DefaultExecutionEnvironment` and
with the deferred startup actions run in the calling process, the way
`SmalltalkImage>>snapshot:andQuit:` arranges it. Writing the image between the stop and the
start is also what keeps it clean: the build run gets Pharo's chrome back when its own session
restarts, the saved image never sees it.

Calling Pharo's `snapshot:andQuit:` directly would be tidier, but its `ChangesLog` bookkeeping
writes to files the browser FS does not provide.

### When a startup script does nothing at all

The failure mode to know: the image boots as plain Pharo, IDE and all, and nothing anywhere
says why. Three different causes produced exactly that picture here.

**Compiling asks who you are.** `compile:classified:` makes Pharo open the *Author
identification* dialog, and a startup script has nobody to answer it, so it waits there
forever. Set the author first — and set it through `Author uniqueInstance fullName:`, because
the class-side `fullName:` validates the string and can raise the very dialog you are
avoiding.

**A bare `!` inside a comment closes the chunk.** The rest of the comment then parses as code.
This bites hardest inside a doit, where everything after the accidental break runs as separate
chunks against variables that no longer exist. In chunk format that character has to be
doubled. `utils/check-chunks.py` reads a file the way the chunk reader does and reports any
chunk whose comment quotes do not balance — run it before spending a build on the image.

**Naming a global that does not exist fails at compile time**, before any `on: Error` around
it can catch anything. Reach for such a class through `Smalltalk at: #Name` instead.

All three look identical from outside, so do not reason about which one it is: have the script
write its progress to a file after each step. An image with no IDE has no other way to tell
you where it stopped.

Keeping the app in one file matters too. An earlier `app-build.st` held its own copy and
quietly fell behind — no `handlesMouseMove:` (so no dragging), a leftover diagnostic morph,
and the field added with `openInWorld` instead of `addMorphBack:`, which puts a full-screen
sheet in front of the bubbles and swallows their clicks.

### Known limitation, and it is not the snapshot's

Morphic runs a burst of cycles whenever an input event arrives and stands still in between,
so the bubbles drift only while you are touching them. **The boot-built bundle behaves exactly
the same** — two screenshots two seconds apart are byte-identical for both, and from inside
the resumed image a bubble's `position` is unchanged 1.2 seconds later. So this is a property
of Morphic stepping under SqueakJS, not something snapshotting introduced.

Ruled out along the way, each by measurement rather than reasoning: stale step-list clock
times (re-registering all 18 steppers changes nothing, and `WorldState>>adjustWakeupTimesIfNecessary`
already exists for exactly "after a snapshot"); the VM delay timer (a forked probe fires);
deferred startup actions; the execution environment; deferred drawing left switched on; a dead
or suspended UI process (it is alive); and the inter-cycle pause, which `doInterCycleWait`
caps at `interCycleLapse * 2` = 32 ms and therefore cannot stall on the clock jump.

What is left to look at is `WorldMorph class>>doOneCycle`, which cycles
`WorldMorph currentWorld` and `extraWorldList` rather than the `World` global. Note that
respawning the UI process to rebind them is a trap: terminating the old process kills whatever
startup code is doing the rebinding.

**A warning about measuring any of this from outside:** the launcher hands its canvas to the
worker with `transferControlToOffscreen`, and reading that canvas back from the main thread
(`drawImage` + `getImageData`) returns a stale frame — it reported "not moving" for a page
that was demonstrably repainting. Compare screenshots instead.
