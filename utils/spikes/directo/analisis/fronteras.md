## Implicancias para el codegen
- 1-ENTRADA (dónde): el gancho va en executeNewMethod (vm.interpreter.js:1115), inmediatamente después del bloque `if (primitiveIndex > 0) tryPrimitive...` (1129-1131) y antes del decode de header (1135). Razones: (a) es el embudo de TODOS los caminos de send incluidos perform: y executeMethodArgsArray, todos con contrato de pila rcvr+args idéntico; (b) los sends con primitiva exitosa no pagan el chequeo; (c) puesto ahí, el retorno normal (push del resultado, return) hace que el caller clásico jiteado siga inline sin volver al trampolín (su activationCheck jit.js:1252 no dispara). No conviene send() en v1: se perderían los caminos perform/execute y no ahorra nada; la fusión con el cache (v2) sí se hace en send().
- 1-ENTRADA (chequeos exactos): `var f = newMethod.directo; if (f && vm.directoOk && f.numArgs === argumentCount) { ... }`. Protocolo de .directo idéntico a .compiled: undefined (nunca visto) → false (visto, no elegible o 1ª activación) → función; setear method.directo=false junto a method.compiled=false en jit.js:148 para que ambas propiedades entren en la misma transición de hidden class. f.numArgs es una propiedad puesta sobre la función generada (cinturón contra caminos raros tipo prim 84/objectAsMethod; medir y quizá soltar después). vm.directoOk es un booleano del vm (declarado en initVMState por forma estable, patrón de vm.interpreter.js:94-99) que apagan logSends/breakOn/breakOnSendOrReturn/single-step. NO hace falta chequeo de 'deopt en curso': la cadena deoptInner/deoptOuter se construye solo con returns, sin sends intercalados posibles (materializar no envía; allocateOrRecycleContext no dispara GC); assert vm.deoptInner===null en build de debug.
- 1-ENTRADA (costo y fusión con el cache): v1 paga 1 load + 1 branch por activación no-primitiva (simétrico al newMethod.compiled de 1166; esperado ruido, pero A/B obligatorio por regla del proyecto). v2 lo funde con el methodCache: agregar `directo: null` al literal de vm.interpreter.js:133; findSelectorInClass llena `cacheEntry.directo = newMethod.directo || null` junto a primIndex/argCount (1068-1077); PROTOCOLO CLAVE: quien instala method.directo llama flushMethodCacheForMethod(method) (1403) para refrescar entradas viejas, y toda invalidación también flushea. Con eso, send() (1024-1030) hace `if (entry.directo) { entrada directa }` = cero loads extra para los sends no-directos.
- 2-DIRECTO→DIRECTO (regla dura): PROHIBIDO llamar findSelectorInClass desde código directo — su camino de miss hace popNandPush sobre la pila del VM para cannotInterpret:/DNU (vm.interpreter.js:1063,1091) y en modo directo los operandos no están ahí. El lookup permitido desde un sitio directo es: getClass del receiver (typeof number → clase SmallInteger, si no .sqClass) + findMethodCacheEntry(sel, cls) (1365-1387, sólo sonda) + `e.method && e.primIndex === 0 && e.method.directo` (o e.directo con la fusión v2). Miss del cache o target no-directo ⇒ FRONTERA (materializar + deoptPendiente): el send() clásico del epílogo re-hace el lookup completo con DNU/cannotInterpret sobre la pila real reconstruida. Eso convierte el miss del cache global (rarísimo: 100% de aciertos en benchFib) en una deopt, que es correcta y amortizada.
- 2-DIRECTO→DIRECTO (recomendación IC): v1 con sonda global sola (menos maquinaria de invalidación, valida semántica); v3 agrega IC monomórfico por sitio: celda cerrada sobre la función generada `var S_cls=null, S_fn=null, S_ep=0;` y en el sitio `var cls = typeof x==='number' ? CLASE_SMALLINT : x.sqClass; if (cls===S_cls && S_ep===vm.directoEpoch) r=S_fn(vm,x,...,d+1); else { sonda global; si da directo → llenar celda y llamar; si no → frontera }`. Justificación: en clásico el IC dio 0 porque executeNewMethod dominaba; en directo la llamada es ~una call JS y la sonda global (xor+mask+load+2 compares+store de methodCacheRandomish POR LLAMADA, 1373) pasa a ser el costo dominante del send — el IC son 2 compares. Es inferencia: el proyecto exige A/B pareado antes de creerlo, con filtros de bisección tipo jitSpLocalOnly (jit.js:385-391). Invalidación del IC: exclusivamente por epoch (ver punto 4); IC monomórfico, sitios polimórficos caen a la sonda siempre.
- 3-FRONTERA (regla de pcs, no negociable): todo pc de materialización DEBE pertenecer al conjunto de labels garantizados del código clásico: pc=0 (entrada), pc-después-de-send (jit.js:1255), pc-después-de-jumpIf (jit.js:1045), destino-de-salto (jit.js:1032/1046). NUNCA materializar con pc = pc del bytecode send: ese pc no suele tener label y la reentrada cae en `default: vm.interpretOne(true)` (jit.js:267) → enableSingleStepping recompila el método y breakNow() filtra 'break' al host (vm.interpreter.js:283-294, 1853-1856). Por eso el iniciador de la frontera materializa con pc = pc-DESPUÉS-del-send, repone rcvr+args en SU pila de operandos, y registra el send pendiente para que el epílogo lo re-emita.
- 3-FRONTERA (materializar generalizada, pseudocódigo exacto): `function materializar(vm, method, rcvr, pc, temps, pila) { var ctx = vm.allocateOrRecycleContext(method.methodNeedsLargeFrame()); var p = ctx.pointers; p[0/*sender*/] = vm.nilObj; p[1/*ip*/] = vm.encodeSqueakPC(pc, method); p[3/*method*/] = method; p[4/*closure≡initialIP*/] = vm.nilObj; p[5/*receiver*/] = rcvr; var TFS = 6, n = temps.length; for (var i=0;i<n;i++) p[TFS+i] = temps[i]; for (var j=0;j<pila.length;j++) p[TFS+n+j] = pila[j]; p[2/*sp*/] = vm.encodeSqueakSP(TFS+n+pila.length-1); ctx.dirty = true; if (!vm.deoptInner) vm.deoptInner = ctx; else vm.deoptOuter.pointers[0] = ctx; vm.deoptOuter = ctx; return DEOPT; }`. Batería obligatoria: recursión elegible de 100k+ en Node Y EN WORKER (el worker es default de producción y su stack puede ser menor; Safari aparte): debe deoptimizar cada `cap` frames, seguir clásico, reentrar directo, y dar resultado exacto.
